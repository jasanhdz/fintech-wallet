# Objetivo

Construir una billetera local de producto mínimo para que una persona gestione cuentas MXN propias y realice transferencias internas seguras desde web y móvil conforme al challenge y al contrato OpenAPI existente.

# Scope

## Incluido

- Monorepo npm workspaces con API Express/TypeScript strict/TypeORM/PostgreSQL, web React/Vite y app React Native nativa con Expo; contrato compartido derivado de OpenAPI.
- Web: registro y login; cuenta MXN creada al registro; resumen de cuentas/saldos; historial filtrable por fecha/tipo y cursor; alta/lista de beneficiarios con CLABE de 18 dígitos y checksum; transferencia a beneficiario interno o cuenta propia, revisión, OTP simulado según política configurable y recibo/estado.
- Móvil: login solamente (sin registro); cuentas/saldos; últimos 20 movimientos y detalle; transferencia a beneficiario registrado en web; OTP simulado; recuperación de resultado incierto consultando/reintentando el mismo intento con idéntica llave de idempotencia; tokens en Expo SecureStore/Keychain y ocultamiento de contenido sensible al pasar a background. UI React Native nativa, sin WebView.
- Estados loading, empty, error y access denied, además de validación, saldo insuficiente, límite, OTP, desconexión/estado incierto y sesión expirada; web responsive y accesible (teclado, etiquetas y contraste básico).
- Importes en unidades menores enteras `bigint` en PostgreSQL y cadenas decimales JSON (`amountMinor`); rechazo de más de dos decimales de entrada sin redondeo y sin aritmética `float` en ninguna capa financiera.
- Auth con contraseñas hasheadas, access JWT corto, refresh rotativo, rate-limit, controles owner/auth, protección CSRF/origin para cookie web, requestId, errores `application/problem+json` según el contrato RFC 7807 y logs estructurados con redacción.
- Migraciones TypeORM con `synchronize: false`; transacciones atómicas, locks deterministas de cuentas y del consumo diario, idempotencia persistida, rechazo de saldo negativo, ledger append-only y balanceado, y auditoría append-only protegida por privilegios de BD.
- Pruebas unitarias necesarias y de integración contra PostgreSQL real, incluyendo 100 transferencias simultáneas y seed de al menos 100,000 movimientos con evidencia real de `EXPLAIN ANALYZE`.
- Implementación visual basada en los diseños aprobados como referencias W01–W14/M01–M12 y el mapa `docs/design-mapping.md`. Los estados faltantes y responsive se resuelven y prueban en la app; no copiar HTML/capturas a código. No afirmar exportación visual como evidencia de dispositivo.
- Fixture local de desarrollo aprobada: dos cuentas propias y asientos contraparte balanceados de apertura. Seed idempotente, limitado al entorno local autorizado; valores son solo datos demo/test, no saldo de usuario ni política del producto.

## Excluido

SPEI real, conexiones a bancos, CEP/Banxico, KYC o afirmaciones de identidad/seguridad/garantía; beneficiarios fuera de la plataforma; inversiones; gestión de límites por usuario; biometría; transferencias programadas; exportación de estados; AWS/despliegue cloud; túneles públicos; EAS build/publish y distribución en tiendas. No incorporar extras visuales o claims de los exports que excedan el challenge obligatorio.

# User flows

Los nombres, parámetros, esquemas y respuestas HTTP se rigen por `specs/openapi.yaml`; no se añade una API paralela ni se cambian sus códigos. Para los errores se preserva RFC 7807 y requestId. Cualquier inconsistencia del contrato queda registrada en Assumptions para el Coordinator.

1. **Registro web:** visitante abre `/register`, introduce nombre completo, email y contraseña según `RegisterRequest`; consulta/procesa CSRF de `/auth/csrf`; envía `POST /auth/register`. Éxito crea usuario y una cuenta MXN, entrega sesión según contrato y navega a `/accounts`; error muestra validación/conflicto/rate-limit sin revelar datos sensibles. No hay registro móvil.
2. **Login y sesión:** usuario en `/login` web o login móvil introduce email/contraseña y client `web`/`mobile`; `POST /auth/login`. Web conserva access JWT solo en memoria y refresh en cookie HttpOnly con SameSite más controles CSRF/origin; móvil conserva tokens solo en SecureStore/Keychain. Refresh usa `POST /auth/refresh`, logout `POST /auth/logout`, identidad `GET /auth/me`. Sesión vencida/revocada conduce a relogin. No localStorage ni AsyncStorage para tokens.
3. **Cuentas:** pantalla web `/accounts` o inicio móvil solicita `GET /accounts`; presenta solo cuentas del usuario, saldo disponible MXN y loading/empty/error. Un recurso ajeno se deniega sin revelar su existencia. Registro no implica fondos iniciales; los importes de fixture local no son saldos de producción.
4. **Beneficiarios web:** `/beneficiaries` lista `GET /beneficiaries`; `/beneficiaries/new` recibe nombre, alias y CLABE; valida 18 dígitos/checksum y envía `POST /beneficiaries`. Solo se registra si resuelve a cuenta interna; muestra CLABE enmascarada y errores del contrato. Acceso/selección de beneficiario ajeno se deniega. Móvil únicamente elige uno ya registrado mediante `GET /beneficiaries`.
5. **Historial web:** desde cuenta se solicita `GET /accounts/{accountId}/movements` con filtros opcionales `from`, `to`, `type`, `limit`, `cursor`. Mostrar página/cursor estable, continuar sin OFFSET, estados loading/empty/sin resultados/error conservando filas cargadas. Acceso solo a cuenta propia.
6. **Historial móvil:** seleccionar cuenta y solicitar el mismo endpoint con `limit=20`; presentar hasta los últimos 20 movimientos autorizados. Abrir detalle de movimiento con los datos disponibles de la respuesta/transferencia; errores y desconexión son recuperables.
7. **Transferencia web o móvil:** elegir cuenta origen propia y destino: beneficiario interno (móvil solo esta opción) o cuenta propia (web); introducir importe MXN de precisión máxima dos decimales, concepto y referencia numérica. Revisar datos y enviar `POST /transfers` con `Idempotency-Key` aleatoria, única para el intento y retenida para cualquier retry exacto. Bloquear doble submit. Respuesta `201` completada o `202` `awaiting_confirmation`; errores RFC 7807 de validación, autorización, idempotencia, saldo/límite se muestran sin exponer internals. Rechazar origen=destino.
8. **OTP/confirmación:** cuando la policy config determine desafío, `POST /transfers` crea intento pendiente sin débito/crédito. La UI solicita OTP simulado ligado a ese `transferId`; `POST /transfers/{transferId}/confirm` con código e idempotency key según OpenAPI. OTP correcto dentro de expiry y policy válida confirma atómicamente; incorrecto/expirado o intentos agotados muestra error y mantiene operación sin asientos. No exponer código OTP en logs; mecanismo de prueba no publica códigos en salida de logs.
9. **Recibo y recuperación:** consultar `GET /transfers/{id}` para estado real/recibo interno. Web navega a recibo y permite volver a historial. En pérdida de conexión móvil, conservar la misma clave y payload del intento; consultar estado y repetir la misma operación/key cuando corresponda hasta conocer estado definitivo, sin duplicar postings. DB outage se presenta como error recuperable; retry conserva idempotency key.
10. **Privacidad móvil:** al pasar background/app switcher ocultar el contenido sensible; al volver foreground reanudar sesión válida o pedir login si expiró/revocó.

# Modelo de datos

Tipos son conceptuales; el esquema concreto se implementa en migraciones TypeORM PostgreSQL. IDs UUID, tiempos `timestamptz`, dinero `bigint` en minor units. Todas las relaciones con owner se validan en servicio/consulta y en constraints donde sea posible.

- **users**: `id uuid PK`, `email citext/varchar UNIQUE`, `full_name varchar(120)`, `password_hash text`, `created_at timestamptz`, `updated_at timestamptz`; identidad y propietario de recursos.
- **accounts**: `id uuid PK`, `owner_id uuid nullable FK users`, `name varchar`, `kind enum(checking,savings,clearing)`, `currency char(3) CHECK MXN`, `balance_minor bigint`, `clabe varchar(18) UNIQUE`, `created_at timestamptz`. Cuentas customer no permiten saldo negativo; clearing de contraparte puede tener signo según apertura/postings. Una cuenta MXN se crea atómicamente con registro. Clearing no pertenece a usuario.
- **beneficiaries**: `id uuid PK`, `owner_id uuid FK users`, `destination_account_id uuid FK accounts`, `name varchar(120)`, `alias varchar(80)`, `clabe_encrypted o protegido varchar(18)`, `created_at timestamptz`, unicidad adecuada de CLABE/destino por dueño. CLABE validada por checksum y vinculada a cuenta interna; respuestas/logs nunca exponen valor completo.
- **transfers**: `id uuid PK`, `owner_id uuid FK users`, `source_account_id uuid FK accounts`, `destination_account_id uuid FK accounts`, `beneficiary_id uuid nullable FK beneficiaries`, `amount_minor bigint CHECK >0`, `currency char(3) CHECK MXN`, `concept varchar(40)`, `reference varchar(1..7 digits)`, `status enum(awaiting_confirmation,processing,completed,rejected)`, `created_at`, `completed_at nullable`, `receipt_reference nullable`, `request_id`. Impedir origen y destino iguales. Estado pendiente no genera asientos.
- **ledger_entries**: `id uuid PK`, `transfer_id uuid FK transfers nullable para apertura`, `account_id uuid FK accounts`, `signed_amount_minor bigint CHECK <>0`, `currency char(3)`, `entry_type`, `created_at timestamptz`; postings append-only. Cada transferencia completada tiene débito/crédito que suman cero; entradas de apertura también se contrapartidan a clearing. Trigger/constraint diferible o mecanismo equivalente en BD impone balance por transferencia; actualización de saldos materializados ocurre en la misma transacción.
- **daily_limit_usage**: `owner_id uuid FK users`, `business_date date`, `currency char(3)`, `outgoing_minor bigint CHECK >=0`, PK (`owner_id`,`business_date`,`currency`). Fila bloqueada/transaccionalmente actualizada para aplicar límite concurrente en zona IANA configurada.
- **idempotency_records**: `id uuid PK`, `user_id uuid FK users`, `operation varchar`, `key_hash` o clave protegida, `payload_hash`, `transfer_id uuid FK transfers`, `response/status snapshot`, `created_at`, `expires_at`; unique (`user_id`,`operation`,`key_hash`). Igual clave+payload recupera resultado original; payload diferente conflictúa. Una clave de confirmación no crea otro intento.
- **otp_challenges**: `id uuid PK`, `transfer_id uuid UNIQUE FK transfers`, `code_hash`, `expires_at`, `attempt_count`, `max_attempts`, `consumed_at nullable`, `created_at`; atado a un solo intento, un solo uso, valores de expiry/retries configurados; jamás guardar/loggear código plano.
- **refresh_sessions**: `id uuid PK`, `user_id uuid FK users`, `token_hash UNIQUE`, `client`, `expires_at`, `rotated_at/revoked_at nullable`, `created_at`; rotación invalida token anterior y permite detectar reutilización conforme policy de sesión.
- **audit_events**: `id uuid PK`, `actor_id uuid nullable FK users`, `action`, `resource_type`, `resource_id`, `request_id`, `metadata jsonb redactado`, `created_at`; append-only. Rol runtime sin privilegios UPDATE/DELETE; migrator separado.

Índices para owner/cursor/fecha/tipo en movimientos (`account_id`, `occurred_at`, tie-breaker UUID) y tablas de idempotencia/límite/sesión. Locks de cuentas por UUID ascendente y fila usuario/fecha de límite dentro de transacción; retry acotado en errores recuperables de serialización/deadlock preservando key. `wallet_test` fail-closed para integración, concurrencia, seed 100k y EXPLAIN; nunca ejecutar fixtures de prueba contra `wallet_dev`.

# Assumptions

- Este es un ciclo Forge nuevo de producto. BOOT-00 y su evaluación 3/3 permanecen como historial; `docs/forge/BOOT-00-FINDINGS.md` no representa evaluación del producto.
- El challenge obligatorio, `specs/requirements.md` y decisiones expresamente aprobadas por el usuario gobiernan alcance. Referencias W01–W14/M01–M12 están aprobadas exclusivamente como guía visual y `docs/design-mapping.md` documenta fuentes/estados/capturas faltantes; no se copia HTML ni se convierten ejemplos en reglas funcionales.
- El usuario aprobó crear cuenta MXN al registrarse y fixture local con dos cuentas propias y contra-asientos de apertura. El fixture solo es demostración/test, no define saldo, política o garantía para clientes. No hay saldo de apertura implícito en registro de producción.
- CLABE beneficiaria válida solo puede resolverse a una cuenta interna; transferencia solo a beneficiario interno o cuenta propia. No hay flujo externo SPEI/bancos.
- Importe con más de dos decimales se rechaza, no se redondea. Importe se entrega en JSON como `amountMinor` decimal-string y BD bigint. Límite de magnitud se valida contra rango bigint/config antes de parsear.
- Umbral de límite diario, zona de negocio, umbral OTP, expiry/reintentos/lockout OTP y parámetros operativos siguen pendientes de política de producto; configurables y exigidos explícitamente en producción. Los ejemplos demo no están aprobados. No se fija valor de garantía o challenge.
- El OTP simulado debe ser verificable localmente sin revelar valores secretos en logs. Su canal/mecanismo de prueba se mantiene interno/configurado; no se inventa password ni salida OTP.
- Ante mismo origen/destino, rechazar transferencia. Día de negocio se asigna usando instante de aceptación y zona IANA configurada; límites se aplican serializadamente en ventana local [inicio, fin).
- OpenAPI ya committed es contrato de Coordinator. Posibles cuestiones a resolver por Coordinator sin edición unilateral en esta tarea: `GET /accounts/{accountId}` y `GET /beneficiaries/{beneficiaryId}` existen en contrato además de la superficie resumida por el usuario; refresh móvil documenta body pero el login describe entrega de refresh y logout/confirm idempotency semantics necesitan precisión; códigos existentes limitan cómo representar validación/reglas y algunos responses no enumeran todos los errores. Implementar de forma compatible con contrato y registrar discrepancia para coordinación, sin inventar endpoint/código o alterar OpenAPI.
- Los pasos de inicio siguen README y scripts reales. No se afirma que pruebas hayan pasado hasta ejecutar y conservar evidencia; no usar mocks como prueba de integración.

# Rubric de evaluación

Cada criterio es binario `PASS/FAIL`; PASS requiere ejecutar la comprobación indicada y conservar evidencia reproducible. Un diseño, mock, export Expo o inspección estática no reemplaza prueba de flujo integrado. Playwright/curl y comandos se ejecutan con servicios locales; no se despliega ni publica.

1. **Stack reproducible:** con Node `26.13.1`, `npm ci` instala workspaces y `npm run lint`, `npm run typecheck`, `npm test`, `npm run build` terminan con código 0 según cobertura de proyectos configurada. **PASS/FAIL**.
2. **Registro a cuentas:** Playwright registra usuario nuevo en web contra API/PostgreSQL real; se crea exactamente cuenta MXN inicial, sesión válida y resumen lista sus cuentas/saldo; login y `/auth/me` funcionan, sin registro móvil. **PASS/FAIL**.
3. **Sesión, tokens y controles:** inspección de flujo web confirma access solo memoria, refresh HttpOnly/SameSite, CSRF/origin y ningún token en localStorage; móvil usa SecureStore/Keychain y ningún token en AsyncStorage; refresh rota y reutilización/revocación se trata; rate-limit login aplica; requestId presente. **PASS/FAIL**.
4. **Owner/access denied:** con dos usuarios, curl/API intenta leer/usar cuenta, beneficiario, transferencia e historial del otro; cada caso es denegado con respuesta del contrato sin filtrar contenido ni existencia, incluyendo UI access-denied/session states. **PASS/FAIL**.
5. **Beneficiario web/CLABE:** flujo Playwright crea/lista beneficiario interno con CLABE válida y checksum; CLABE malformada/checksum inválido y duplicado/destino no interno se rechazan sin persistir; CLABE queda enmascarada en respuestas/logs. **PASS/FAIL**.
6. **Transferencia web completa:** Playwright con API/PostgreSQL real recorre beneficiario → importe/concepto/referencia → revisión → confirmación/OTP cuando corresponde → recibo → movimiento en historial; otra ruta transfiere entre cuentas propias. Recibo es interno. **PASS/FAIL**.
7. **Transferencia móvil completa:** simulator/device verifica login (sin registro), saldo/cuentas, últimos 20, detalle, selección de beneficiario creado en web, revisión, OTP y resultado/recibo usando backend/PostgreSQL reales. 8. **Doble click/idempotencia:** enviar doble click y repetir misma key+payload devuelve el mismo intento/resultado y un solo débito/crédito; misma key con payload distinto produce conflicto según OpenAPI. Evidencia de BD confirma unicidad. **PASS/FAIL**.
