# Diseño aprobado → pantallas → estados → entregas

> Esta copia de entrega no contiene los assets visuales. Las referencias PNG sanitizadas correspondientes están en la rama `design-reference` (tag `design-reference-v1`). Los paths `../design/**` de las filas conservan los nombres de origen del proyecto original; el HTML crudo no se versiona en esta copia.

## Aprobación y límites

El usuario aprobó los diseños web y móvil de `design/` como **referencia visual para desarrollo** el 2026-11-14. Las diferencias visuales menores se resolverán durante la implementación; responsive y comportamiento real se verificarán con la aplicación. La aprobación no convierte el HTML exportado en código ni aprueba las reglas/claims que contiene. Se implementan los requisitos de `docs/challenge.md` y `specs/requirements.md`; se excluyen SPEI/bancos externos, inversiones, garantías financieras/regulatorias, servicios Banxico/CEP, gestión de límites, biometría y demás bonus no autorizados.

**Fuentes inspeccionadas:** 59 HTML W01–W14 y 49 capturas web disponibles; 22 HTML y 22 capturas M01–M12, además de los dos `DESIGN.md` visuales. Todas las variantes HTML y capturas disponibles se abrieron e inspeccionaron, incluyendo una revisión de dependencias/handlers y de contenido sensible o ilustrativo. Faltan capturas en 10 variantes web; se informa por pantalla abajo. El HTML/capturas contienen datos demo, handlers simulados, dependencias CDN y, en algunas variantes, códigos de prueba; no se copiarán literalmente ni se usarán como endpoint/mock final.

Los originales permanecen en el árbol local de trabajo y no se incluyen en Git: el HTML contiene contraseñas/códigos OTP demostrativos en texto plano y las capturas muestran datos financieros de ejemplo. Se conservan intactos; los paths exactos a continuación permiten revisarlos en el checkout coordinador. `.gitignore` continúa excluyendo capturas (`*.png`). Para una revisión independiente fuera de este entorno, solicitar/adjuntar los exports originales por un canal de diseño seguro.

Los IDs identifican exportaciones de Stitch; las URLs siguientes son **rutas internas propuestas**, no URLs de Stitch. Fases verticales: **1** sesión/cuentas, **2** beneficiarios, **3** transferencias/confirmación/recuperación, **4** historial/comprobantes/seguridad transversal.

## Contradicciones registradas para implementación

1. **Fuentes visuales de color:** los tokens YAML de ambos `DESIGN.md` y capturas coinciden en superficies azul-pálido/primary cobalt; el texto narrativo de ambos archivos propone otra paleta neutra/azul. Precedencia de implementación: capturas + tokens YAML; se conservan los radios, escalas y tipografía Inter. La diferencia queda registrada, no bloquea layout/comportamiento.
2. **Estados sin captura:** falta PNG para W07 (6: duplicado, campos inválidos, CLABE incorrecta, destino no disponible, guardando y error recuperable), W09 own-account review (1) y W10 incorrecto/expirado/verificando (3). HTML fue inspeccionado; esos estados se implementan a partir de contenido y componentes vecinos, y responsive se valida en la app real.
3. **Pares desalineados:** W12 own-account tiene imagen completa y `code.html` sin markup; W07 guardando HTML vacío y error recuperable sin markup. Se adaptan componentes equivalentes, no se reutiliza código Stitch.
4. **Cifras/datos de escenarios:** saldos, nombres, referencias, códigos, límites y tiempos se contradicen. Son ejemplos visuales. No se convierten en política ni seed literal; el backend suministra estados y una fixture local explícita.
5. **Alcance externo y claims:** se ignoran UI/copy de SPEI real, BBVA/otros bancos, Banxico/CEP, KYC/identidad verificada, garantías de fondos/seguridad, inversiones, administración de límites, biometría, export mensual y programación. La transferencia es entre cuentas propias de la plataforma o beneficiarios internos verificados.
6. **Estados OTP/transacción:** umbral/expiry/reintentos que aparecen en exports son ejemplos. El OTP es simulado y ligado a `transferId`; se usan valores de configuración demo documentados, sin código fijo de exports ni datos sensibles en logs.
7. **Móvil nativo:** los HTML no son UI móvil ejecutable. M01–M12 se implementan con React Native nativo, safe areas/tap targets y viewport de dispositivos; no WebView.

## Fases y propietarios de implementación

- **Fase 1:** WEB W01–W03 + MOBILE M01–M02 + API auth/accounts. Registro web, login web/móvil, sesión segura, cuentas/saldos.
- **Fase 2:** WEB W06–W07 + MOBILE M05 + API beneficiaries. CLABE válida y solo cuentas de esta billetera.
- **Fase 3:** WEB W08–W11 + MOBILE M06–M09 + API transfers. Confirmación, límite configurable, OTP simulado, transacción, idempotencia, recuperación del mismo intento.
- **Fase 4:** WEB W04–W05/W12–W14 + MOBILE M03–M04/M10–M12 + API history/receipts/security. Cursor, detalle/comprobante interno, privacidad foreground/background y estados.

Todos los elementos quedan autorizados dentro del alcance obligatorio del challenge, sujeto a que las reglas de diseño no contradigan `specs/requirements.md`. Las variantes de bonus/out-of-scope arriba no se implementan.
